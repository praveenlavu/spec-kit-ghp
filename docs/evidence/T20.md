## Mismatches (new tasks)

No MISMATCH changed what a verb did in this run (everything passed). Findings to turn into tasks; none was fixed here (live tasks change no product code):

1. Issue-list lag hides a fresh issue for about 2 to 4+ s. Endpoint `GET repos/{o}/{r}/issues?state=all&sort=created&direction=desc&per_page=100`; expected (code): a just-created issue is in the newest list; live: absent at the first read, listed 2.3 s after polling started (that clock started after `issues.create` returned; two samples, one per run; see the bullet above). Modules: `issues._find` (the marker search after an unknown-outcome create: it read once, found nothing, and raised the original error, which is the safe direction, but then the caller re-ran) and `push._existing` (a `ghp push` re-run shortly after a LOST create could miss the unlinked task and create a second one, but `push._existing` looks at the story's sub-issue list first, whose lag was not measured, and push sends the parent in the create request; so the duplicate-on-re-run risk is UNQUANTIFIED, not shown). Task: wait and re-read for about 10 s before concluding that nothing carries the marker, and tell the operator to wait; add a test with a fake list that lags (done in T20a).
2. Repeated `POST .../sub_issues` for a child already attached to the same parent is a 422, not a success. Module: `issues.add_sub_issue`: a 422 is not `maybe_applied`, so it raises `E_GH_HTTP` even though the wanted state exists. This can only happen if the child was linked between the plan's read and the write (push creates tasks with the parent in the same request), so it is a narrow race. Task (optional): on a 422 re-read the child and return when its parent is already this parent.
3. Doc drift: the header comment of `src/ghp/issues.py` still lists as UNVERIFIED the reply of the sub-issue POST, the unknown label, the repeated POST and the list order after a create; the header of `src/ghp/activate.py` and `push.py` lists the unverified items too. Update them in a doc-comment task from this file (VERIFIED: reply is the parent issue; label created with push access; repeated POST 422; list lag about 2 to 4+ s), and keep the dropped-label branch and the 300-issue window as UNVERIFIED (done in T20b).
4. Observation, cause UNVERIFIED: the "Item added to project" workflow's `Todo` does not always appear in the Status history of an issue the product adds. For tasks (pushed) it did (`"" -> Todo` by `github-project-automation`). For the story added by `ghp activate` it appeared in run A (`"" -> Todo` by automation, then `Todo -> In Progress` by `praveenlavu`) and not in run B (only `"" -> In Progress` by `praveenlavu`); the final Status was `In Progress` both times. Likely an ordering race between the automation and our write; it changes nothing the verbs promise, but a doc must not say that activate "moves Todo to In Progress" for an issue that was not on the board.
5. The comment POST reply has two keys no fixture holds (`minimized`, `pin`); nothing reads them.
